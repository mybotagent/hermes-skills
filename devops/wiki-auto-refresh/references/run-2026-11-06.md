**증상:** `LOG.md`는 2026-11-05 18:00 미국 증시 브리핑 크론(`2916cc9c2ceb`)이 생성한 페이지로 index.md에 등록·git add되어 있으나(11-05 실행에서 P34로 조치), 11-06 18:00에 해당 크론이 `completed`로 실행된 뒤에도 **LOG.md mtime이 2026-11-05 20:06에 고정**되어 있다.

**원인:** 해당 크론의 프롬프트는 "Fair Value 분석 → stdout 읽기 → 브리핑 리포트 작성 → Discord로 전송"까지만 정의. **LOG.md 기록 단계가 없다.** 11-05의 LOG.md 생성은 별도 경로(또는 수동 실행)를 통해 이루어졌고, 이후 일일 갱신 경로가 없다.

**왜 index 감사로는 안 잡히는가:**
- `index-md-audit.py`는 registered N = actual N / dead link / missing만 검사 → **등록된 페이지가 갱신되지 않는 경우는 판정 범위 밖**
- `stale-audit.py`는 frontmatter `updated:`를 SSOT로 보므로 frontmatter가 갱신되지 않으면 stale로도 안 잡힘 (11-05에 생성 후 updated: = 2026-11-05)

**탐지 절차:**
```bash
ls -la ~/.hermes/wiki/LOG.md   # mtime이 크론 실행일보다 오래됐는지 확인
python3 -c "
import sqlite3
c=sqlite3.connect('/home/ubuntu/.hermes/cron/executions.db')
for r in c.execute(\"SELECT job_id, started_at, status FROM executions WHERE job_id='2916cc9c2ceb' ORDER BY started_at DESC LIMIT 3\"): print(r)
"
```

**조치:** wiki-auto-refresh의 직접 조치 대상은 아님(잔재 없음). **해당 크론 프롬프트에 "LOG.md append" 단계를 추가**하거나, daily report cron이 자체적으로 wiki에 기록하도록 jobs.json 프롬프트를 수정해야 한다.

**교훈:** "페이지가 있는데 갱신되지 않는" 상태는 등록 감사·stale 감사로 잡히지 않는다. cron 산출물이 wiki 페이지인 경우, **cron 실행 기록과 페이지 mtime을 교차 확인**하는 별도 체크가 필요하다.
